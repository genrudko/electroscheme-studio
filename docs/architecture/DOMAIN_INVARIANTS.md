# Domain Invariants — ElectroScheme Studio

These rules define the non-negotiable behavior of the engineering document model. They apply regardless of the selected desktop shell or UI framework.

## 1. Document identity and versions

1. Every project has a stable project ID.
2. Every saved document declares a supported `schema_version`.
3. Schema changes require explicit migrations.
4. Opening an unsupported newer schema is fail-closed and must not overwrite the file.
5. A successful no-op open/save round trip must preserve engineering semantics.
6. A failed save must not replace the last known-good project file.

## 2. Stable object identity

1. Every sheet, layer, object, port and connection has a stable unique ID in its scope.
2. Display labels and equipment names are not identifiers.
3. Renaming an object must not break connections or references.
4. Copying creates new IDs while preserving intended internal relationships within the copied fragment.
5. Deleting an object follows an explicit reference policy and cannot leave silent invalid references.

## 3. Sheets and layers

1. Every placed object belongs to exactly one sheet and one layer unless a future accepted contract defines cross-sheet objects.
2. A hidden layer remains in the engineering model.
3. A locked layer rejects document mutations to its objects unless explicitly unlocked through a command.
4. A non-printable layer is excluded from print/export but not from editing/persistence.
5. Sheet units and dimensions are engineering coordinates, independent from screen pixels.

## 4. Engineering objects

1. A placed symbol is an instance of a known symbol definition/version or an explicitly preserved unresolved reference.
2. A symbol instance stores properties and parameters separately from geometry generated by the renderer.
3. Visual geometry alone cannot define object type, state or electrical meaning.
4. Object transformations use explicit position, rotation and mirror/scale policies.
5. Non-uniform scaling is forbidden for symbol bodies unless the definition explicitly allows it.
6. Stretchable leads or parameterized parts must not distort locked symbol body geometry.

## 5. Ports and terminals

1. Electrical connections terminate at stable port references, not incidental SVG coordinates.
2. A port belongs to exactly one object/definition context.
3. Port location is derived deterministically from definition geometry, instance parameters and transforms.
4. Rotation/mirroring updates port position and direction without changing port identity.
5. Generated busbar/bay ports have deterministic IDs based on stable slot identity, not array position alone.
6. Port compatibility rules are explicit and testable.
7. A missing referenced port is a structured integrity error, never silently converted to a free coordinate.

## 6. Connections and topology

1. Topology is authoritative; rendered lines are its presentation.
2. Connection endpoints reference ports or an explicitly modeled junction/free endpoint type.
3. Moving or rotating an object preserves endpoint references.
4. A visual crossing is not an electrical junction unless the model declares a junction.
5. Deleting an endpoint object applies a defined cascade, detach or reject policy through a command.
6. Duplicate or incompatible connections produce diagnostics according to connection rules.
7. Route waypoints may change without changing electrical endpoint identity.
8. Autorouting must not change topology.
9. Undo/redo of connection operations restores exact endpoint semantics.

## 7. Commands and transactions

1. Every accepted document mutation is executed through a command or transaction.
2. A command either completes atomically or leaves the document unchanged.
3. A command validates preconditions before commit.
4. Undo restores the previous document semantics, not merely approximate visual placement.
5. Redo reapplies the same accepted semantics deterministically.
6. Compound user actions can be grouped into one transaction.
7. Ephemeral UI state is not added to the document command history unless it changes saved engineering data.
8. Autosave never observes a partially applied command.

## 8. Properties and parameters

1. Property definitions have stable IDs, types, units and validation rules.
2. Display names may be localized without changing stored property IDs.
3. Numeric values store canonical units; UI formatting/conversion is a projection.
4. Required properties produce diagnostics when absent.
5. Unknown properties from a newer or external definition must be preserved where safe rather than silently discarded.
6. Parameters affecting geometry must regenerate geometry and ports deterministically.
7. State changes must use the allowed state vocabulary of the symbol family.

## 9. Symbol definitions and provenance

1. Every accepted symbol definition has a stable ID and version.
2. Imported/generated drafts cannot be used as accepted core definitions without promotion evidence.
3. Provenance includes source format, source identifier/file, extraction/conversion version and review status.
4. ShapeSheet-derived geometry and connection points retain enough source metadata for audit and correction.
5. Updating a symbol definition requires an instance migration/compatibility decision.
6. A library update must not silently change existing project appearance or topology without migration consent.
7. The project records or packages the symbol definition versions needed to reproduce its output.

## 10. ГОСТ/СТО profiles

1. A presentation/validation rule belongs to a named profile/version.
2. Every normative rule records its source and applicability boundary.
3. Profile selection does not alter electrical topology.
4. Color, line, text and frame rules are deterministic for a given profile.
5. Rules with incomplete normative certainty are marked advisory/review-required rather than mandatory.
6. The application must distinguish product validation from formal expert approval.

## 11. Persistence and portability

1. The same supported project file opens on Windows and Linux with equivalent engineering semantics.
2. OS path separators, font availability and locale must not corrupt stored data.
3. Serialization order is deterministic where practical to support meaningful diffs and reproducibility.
4. Timestamps and machine-specific metadata do not create semantic diffs unless intentionally changed.
5. Embedded/referenced assets use portable identifiers and explicit packaging rules.
6. Autosave/recovery files cannot overwrite the canonical project without user-visible recovery flow.
7. Backups are created before destructive migration.

## 12. Rendering and dimensions

1. Engineering coordinates and printed dimensions do not depend on display DPI.
2. Zoom/pan affect only viewport projection.
3. Line widths and text sizes follow profile/output rules in physical or canonical units.
4. Interactive overlays are excluded from production export.
5. The same document/profile produces equivalent SVG/PDF output within approved tolerance across platforms.
6. Missing fonts use a controlled fallback policy and generate evidence/diagnostics where output can change.

## 13. Validation and diagnostics

1. Diagnostics use stable rule IDs and object references.
2. A diagnostic must be reproducible from document/profile state.
3. Validation never mutates the document implicitly.
4. Auto-fixes are explicit commands and are undoable.
5. Severity and blocking behavior are defined by rule/profile, not arbitrary UI code.
6. Navigating from a diagnostic selects or locates the referenced object without changing engineering data.

## 14. Import and export

1. Import never overwrites the source or current project silently.
2. Partial import is clearly reported and cannot be promoted as complete without review.
3. Unsupported geometry/formulas are preserved or diagnosed; they are not silently approximated as accepted truth.
4. Export does not modify the project document except explicit metadata through a command.
5. SVG/PDF output must be traceable to project version, profile and application version.
6. Export failure leaves no falsely successful artifact marker.

## 15. Prototype migration

1. Prototype behavior has no compatibility status by default.
2. Reuse requires an asset disposition and accepted migration record.
3. Prototype defects, CSS overrides and duplicate state models are not inherited requirements.
4. Old and new cores cannot both save authoritative project files in the accepted product path.
5. Any reused algorithm must pass new invariant tests independent of prototype UI.

## 16. Security and local-first behavior

1. Core editing does not require network access.
2. Project contents are not transmitted externally without an explicit user action and documented adapter.
3. Opening a project/library validates paths and package contents against traversal and unsafe execution.
4. Imported text/data is treated as data, not executable code.
5. Update and package verification is explicit before pilot/release.
